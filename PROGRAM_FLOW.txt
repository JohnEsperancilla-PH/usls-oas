1. OVERVIEW
================================================================================

USLS OAS lets campus visitors book time with university offices online. The
system handles the full lifecycle of every appointment:

    BOOK  -->  PENDING  -->  APPROVE/DECLINE  -->  GATE ENTRY  -->  ARCHIVE

There are three (3) user types:

  * PUBLIC ("Visitor")
        - Books an appointment through the public site (/).
        - Receives email confirmations and, once approved, an approval email
          that contains the 8-character REFERENCE NUMBER and gate instructions.
        - Presents the reference number at the gate; entry is verified on /entry.

  * SUPER_ADMIN
        - Full control: approve/decline ANY appointment across all offices,
          view the archived (cPanel) history, manage offices, manage admin
          accounts, review the audit log, and configure system settings.

  * OFFICE_ADMIN
        - Scoped to ONE office. Can only view, approve, and decline
          appointments belonging to their own office. Cannot manage system
          configuration.

Two key rules govern the whole system:

  1. Every appointment is written to BOTH databases in parallel:
     - Supabase  = system of record (live data, statuses, emails, audit).
     - cPanel MySQL `appointments` table = archive/mirror copy used by the
       admin "Archived" tab and kept in sync on every create/status change.
  2. A reference number is single-use. After it is verified at the gate it is
     marked USED/COMPLETED immediately and can never be accepted again (unless
     an admin intentionally re-issues it via Reset).

3. APPOINTMENT LIFECYCLE & STATUSES
================================================================================

  +-------------+      approve      +------------+      verify at gate
  |  pending    | -------------->  |  approved  | -------------------->+
  +-------------+                   +------------+                    |
        |                                                            v
        |  decline                                          +-----------------+
        v                                                     |     completed   |
  +-------------+                                            | (reference USED)|
  | declined    |                                            +-----------------+
  +-------------+                                                     |
                                                                      v
                                            reset (re-issue reference,
                                            returns to APPROVED)
                                                                      |
                        expired (date passed) -----------------------+
                                                                      v
                                             archived view = cPanel `appointments`

  STATUS  | MEANING
  --------+-------------------------------------------------------------
  pending | Submitted, waiting for admin review (approve or decline).
  approved| Admin approved + a unique reference number (qr_token) issued,
          | visitor emailed the reference + gate instructions.
  declined| Admin declined; optional decline reason recorded, visitor notified.
  completed| Visitor passed the gate; reference marked used (qr_used_at set).
          | After this point the same code is REJECTED on /entry.
  expired | Appointment date has passed without being used.
  archived| Long-term record copied to cPanel; shown in the Archived tab.

  Single-use enforcement (on /api/scan):
    1. find appointment by qr_token (reference number)
    2. status must be "approved"
    3. qr_used_at must be NULL
    4. date must equal today
    -> PASS: set qr_used_at + scanned_at, status->completed.
    -> Any later attempt returns "Reference number has already been used".

4. PUBLIC FLOW  (Visitor)   -- EXPLANATION
================================================================================

SECTION A.  LANDING / BOOKING FORM  (route: /)
  The public landing page shows a 2-step booking wizard.

  STEP 1 - Personal Information (IdentityForm)
     - Full name, phone, email.
     - "Valid ID to Present at the Guard" - a DROPDOWN of preconfigured ID
       types (school/company/government ID lists). No file upload.
     - Visitor category, purpose of visit (optional).

  STEP 2 - Appointment Request (AppointmentForm)
     - Pick an OFFICE (only offices currently accepting bookings).
     - A calendar month view marks AVAILABLE dates using the office's
       operating days and hours (from the offices table).
     - Pick a TIME SLOT of 30 or 60 minutes; unavailable/overlapping slots
       are blocked, and the office's daily capacity is enforced.
     - Back/Next navigation preserves the entered data.

  On submit, the browser POSTs to /api/appointments. The server:
     - rate-limits the request per IP,
     - re-validates every field (name, phone, email, valid ID value, etc.),
     - verifies the office exists, is accepting bookings, and the chosen
       date/time slot is still open (no double-booking),
     - creates the row with status "pending",
     - MIRRORS the same row to the cPanel `appointments` table in parallel,
     - schedules a booking-confirmation email to the visitor and an admin
       alert (with one-click approve/decline links) to the office admins.

  After a successful POST the visitor sees the
  "Appointment Submitted - pending review" success screen.

SECTION B.  EMAIL STAGE
  The visitor receives:
  1) Booking confirmation  - "we received your request, pending review."
  2) APPROVAL email        - sent once an admin approves. Contains:
        - the 8-character REFERENCE NUMBER,
        - the appointment details, and
        - GATE ENTRY INSTRUCTIONS:
          "Entry is accepted only at USLS Gate 2. Present the {chosen ID}
           at the Guard to receive your visitor's pass."
  3) DECLINE email         - sent if denied (with reason if provided).

SECTION C.  GATE ENTRY  (route: /entry)
  At the gate, the kiosk shows /entry: a single input box for the reference
  number. Submitting POST /api/scan:
     - uppercases/normalizes the reference,
     - looks it up; invalid code -> "Reference number not found",
     - checks status -> not approved -> specific denial message
       (already used / expired / declined / still pending),
     - checks date == today -> error if it is for another day,
     - PASS  -> shows "Entry Approved" with visitor name, office, date,
       time, and the valid ID to present; marks the appointment COMPLETED.
     - USED  -> the moment a code is verified it is DISABLED. Entering it a
       second time returns "Reference number has already been used".

5. SUPER ADMIN FLOW  -- EXPLANATION
================================================================================

The Super Admin signs in at /admin/login using Supabase authentication.
The admin layout verifies the session (GET /api/admin/auth) and loads the
admin's role + office. On the desktop sidebar the Super Admin sees:

  1. APPOINTMENTS  (/admin)          - default dashboard, filter tabs:
        - PENDING    : all pending bookings; Approve / Decline buttons.
                       Decline can include a reason.
        - APPROVED   : list with copyable reference numbers.
        - DECLINED   : declined list.
        - ARCHIVED   : long-term history READ FROM cPanel `appointments`;
                       modal shows details incl. Valid ID; no ID photo.
        - ALL        : everything.
        Approve/Decline actions call /api/appointments/approve and
        /api/appointments/decline. A completed appointment whose reference
        was used can be RESET (re-issue) from its detail modal, which calls
        /api/appointments/reset-qr, returns status to "approved" with a NEW
        reference, and re-sends the approval email.
        Approve/decline also update the cPanel mirror in parallel and fire
        post-task jobs (email, Google Calendar event, email_logs, audit_logs).

  2. OFFICES  (/admin/offices)       - add / edit / enable-disable offices:
        operating days, opening-closing hours, default slot duration,
        daily capacity, contact email/phone, accepting-bookings toggle.

  3. ACCOUNTS  (/admin/accounts)     - create / edit / deactivate admin
        accounts and assign role: super_admin or office_admin (with office).

  4. AUDIT LOG  (/admin/audit)       - read-only trail of every sensitive
        action (approve, decline, reset_qr, account changes, etc.) with
        who/what/when.

  5. SETTINGS  (/admin/settings)     - notification toggles (confirmation,
        admin alert, approval, decline, reference re-send), archive flags
        (which statuses get retained/backfilled to cPanel), and a
        "Sync Now" button that backfills/upserts approved/declined and other
        flagged appointments into the cPanel archive.

  Super Admin scoping:
     - office_id = NULL  -> can act on appointments in EVERY office.
     - Every write is logged to audit_logs; every email outcome to email_logs.

  NOTE: Approve/Decline can also happen OUTSIDE the dashboard via the
  one-click EMAIL LINK. The admin-alert email carries HMAC-signed
  approve/decline URLs. Clicking one PERFORMS THE ACTION IMMEDIATELY (no
  confirm page) and the browser tab auto-closes. Link replay after the action
  just shows "Already reviewed".

6. OFFICE ADMIN FLOW  -- EXPLANATION
================================================================================

The Office Admin signs in the same way (/admin/login + /api/admin/auth).
The system knows their office_id. Key differences from Super Admin:

  SCOPE
     - They only see/act on appointments where office_id == THEIR office.
     - They CANNOT act on another office (403 on approve/decline/reset if
       office_id mismatches).
     - The sidebar shows ONLY the Appointments page; the management pages
       (Offices, Accounts, Audit Log, Settings) are hidden and their APIs
       are super-admin-gated (requireSuperAdmin -> 403).

  DASHBOARD
     - Same 5 filter tabs but filtered to their office:
         PENDING : Approve / Decline (+ reason) their office's bookings.
         APPROVED: copy reference numbers of issued bookings.
         DECLINED / ARCHIVED / ALL : same actions as Super Admin, scoped.
     - Completed appointments can be RESET (re-issue a new reference and
       re-send the approval email) if the visitor never entered the gate or
       the reference was lost/used.
     - ARCHIVED still reads the cPanel `appointments` table, filtered by
       their office_id.

  WORKER BEHAVIOR
     - Approve/decline/reset write to Supabase and mirror to cPanel in
       parallel, exactly like Super Admin.
     - The admin-alert email with one-click links is sent to THEIR office's
       admins when a new booking lands.

  PERMISSION RULES  (enforced server-side in every route)
     - office_admin + their office_id == appointment.office_id  -> allowed
     - office_admin + different office                              -> 403
     - status must be "pending" to approve/decline
     - only "completed" appointments may be reset
     - email action links are office-scoped + HMAC-signed (72h expiry)

8. KEY SECTIONS / ENDPOINTS REFERENCE
================================================================================

  PUBLIC
    /                              landing page + 2-step booking wizard
    /entry                         gate kiosk - reference number input
    POST /api/appointments         create booking (rate-limited, validated,
                                   slot/capacity checked, Supabase + cPanel)
    POST /api/scan                 verify reference; marks USED/completed

  ADMIN (auth required)
    POST /api/admin/auth           validate session + return admin profile
    POST /api/appointments/approve approve pending (add reference)
    POST /api/appointments/decline decline pending (optional reason)
    POST /api/appointments/reset-qr re-issue reference on completed appt
    GET  /api/admin/archived       read cPanel archived appointments
    POST /api/admin/archive-sync   backfill/upsert flagged records to cPanel
                                   (manual "Sync Now" or auto by settings)

  EMAIL ACTION (signed tokens)
    GET/POST /api/appointments/email-action?action=approve|decline&token=...
                                   one-click, executes immediately (72h token)

  SECTIONS (super admin only unless noted)
    /admin/offices                 office CRUD + hours/capacity/contacts
    /admin/accounts                admin accounts + role assignment
    /admin/audit                   audit trail
    /admin/settings                notifications + archive flags + Sync Now

  DATA STORES
    Supabase tables:
      appointments (status: pending | approved | declined | completed |
                    expired; qr_token = reference number; valid_id = ID
                    presented at guard)
      offices, admins, audit_logs, email_logs, settings
    cPanel MySQL:
      appointments (mirror/archive of appointment data; single-use statuses)
